# BeanMora 0.5.32

Google login now keeps a per-tab PKCE verifier across browser reloads and invalid old-session cleanup. The production Auth logs on October 12 showed Google callbacks returning 302, followed intermittently by a PKCE token request with an empty verifier (HTTP 400). The browser adapter keeps durable proof through client initialization, consumes it after the callback, rejects redirects if both browser stores are unavailable, and cleans callback parameters. The registered web and native redirect targets remain unchanged. Native Keychain/Keystore storage and the native callback retry contract are preserved.

The profile has one followers/following entry in its header. The duplicate lower tabs are removed. Profile editing has independent **Hide followers** and **Hide following** settings. Hidden lists and their counts are available only to the owner, including when the viewer is an approved follower. The RPC projection and restrictive raw follow-graph policy enforce these rules on the server.

The eye icon in the profile header opens signed-in profile visitors from the last 30 days, with the latest visit time per account. Own stories show the unique signed-in viewer count and names. Image views are recorded after media loads; video views are recorded after playback starts while the story is active. Own views, anonymous users, blocked users, unavailable private profiles, and expired or rejected stories are excluded. Counts start with this release; no historical views are invented. Viewer lists are visible only to the profile/story owner and paginate in batches of 50. Opening the story viewer list pauses story playback.

Both additive database migrations were applied to the BeanMora project. Rollback-only SQL fixtures validate owner-only access, independent list privacy, raw-query privacy, forged inserts, self/guest/blocked views, duplicate suppression, private-account approvals, story expiry, and the 30-day profile window. TypeScript definitions include only the changed/new schema contracts. No Auth credentials, email, phone or visitor identity is accepted as a client-supplied tracking parameter.

Local validation includes the root unit/recommendation/outcome suites, mobile core suite, root lint, both TypeScript trees, three-platform Expo export, exported dependency isolation, the live redirect probe, and browser regressions for Google callback recovery, profile editing and viewer lists, image/video view recording, and existing social flows. Browser fixtures are isolated test data, not physical-device measurements or a completed sign-in to the user's Google account.

`apps/mobile/.eas/workflows/release-0.5.32.yml` reuses the existing guarded production Expo deploy, iOS build and exact-build-ID TestFlight submission jobs.
